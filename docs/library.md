# Built-in MIDI library

Flowstate ships with a library of MIDI clips made for it, starting with the GodFlow pack. Library clips and AI results are one catalog: the Studio searches, previews, drags and starts ideas from either. Every library clip carries its credit wherever it goes.

The roadmap issue is P1-17. The contracts live in `schema/src/library.ts` (the pack manifest) and `schema/src/bridge.ts` (the catalog and its commands). The analyzer and search live in `core`, and the importer in `library/`.

## Clips as MIDI and as IR

Each clip is stored twice:

- **As MIDI**, normalized: the original notes, exact, at 960 PPQ in a clip of whole bars. Track names and timing come from Flowstate, not from the source file. Preview and drag-out use this, so a clip plays exactly as the producer wrote it.
- **As score IR**, written by `core`'s MIDI→IR analyzer. "Use" puts this in a lineage node, where it can be edited, re-voiced, re-rolled and planned around ("keep the chords, new melody"). The planner also shows it to a model as a style example.

Why both: the IR is what makes a library clip interchangeable with an AI result. It goes into the same lineage, takes the same tweaks, and is read by the model in the language the model writes. But IR is a description, not a recording. Core voices chords itself, so a clip's own voicing comes back close, not identical. Keeping the MIDI means nothing is lost to the analysis. The catalog records how close the IR comes (fidelity, below), so the gap can be seen and measured.

The analyzer is the same one the proposal's "Use what I just played" needs (`PlanRequest.reference`). A library clip can be sent as a reference too.

## Layout

```
library/
  packs/<pack-id>/            one folder per pack (the folder name is the pack id)
    manifest.json             flowstate.libraryPack.v2
    CREDITS.md                credit and license note, quoting the manifest's credit line
    midi/<lane>/<style>/*.mid source files as delivered
  catalog/                    generated by `npm run -w library build`; committed; bundled into the plugin
    catalog.json              flowstate.libraryCatalog.v1 (LibraryCatalog in bridge.ts)
    <pack>--<clip>.mid        normalized clips, flat
  src/                        validation, import, drift check (TypeScript)
```

The plugin embeds `library/catalog/*` with `juce_add_binary_data` and reads files by name through `Platform::libraryResource`. Source files never ship. Only normalized clips do, so source track names, sample-pack names and stray end-of-track markers stay in the repo. The `check` step (and CI) fails when `library/catalog` differs from a fresh build.

## Pack manifest (`flowstate.libraryPack.v2`)

v1's `flowstate.partnerMidiPack.v1` fields are kept where they still make sense. Fields that `core` now measures (meter, bars, energy, density, complexity) are dropped. As in the IR, every key is present and `null` means "not set". JSON Schema: `schema/library-pack.v2.schema.json`.

| Field | Meaning |
| --- | --- |
| `schema` | `"flowstate.libraryPack.v2"` |
| `id` | Pack id, lowercase kebab-case, equal to the folder name |
| `title`, `producer` | Shown with the pack (v1 `pack`, `producer`) |
| `credit` | Attribution line shown with every clip (v1 `license.attributionText`) |
| `creditFile` | Relative path of the credit and license note; it must quote `credit` |
| `license` | `{ id, name, allowsPreview, allowsExport, allowsStyleExamples }` |
| `laneNotes` | Why a lane has no clips (v1 `laneAvailability`), so nothing fake fills it |
| `omitted` | `[{ file, reason }]`: source files deliberately left out |
| `entries[]` | One per clip, below |

| Entry field | Meaning |
| --- | --- |
| `id` | Unique in the pack; the catalog id is `lib:<pack>/<id>` |
| `file` | Relative `.mid` path in the pack (v1 `midiAssetPath`) |
| `lane` | `chords`, `bass`, `melody` or `drums` |
| `title` | Card title |
| `genres` | Style tags in the planner's vocabulary (`hip-hop`, `rnb`, `neo-soul`, `pop`, ...), lowercase kebab-case |
| `tags`, `feel` | Search and ranking hints |
| `tempoMin`, `tempoMax` | Tempo range the clip suits; `null` = the file's tempo ± 8 |
| `key` | `{ tonic, mode }` when the producer knows it; it wins over detection. `null` = detect |
| `notes` | A musical note for people and models |

### Rules

These are v1's rules, carried over. `library validate` enforces each one, and each failure names the field or file it is about:

- **Paths are safe.** A path is relative, uses forward slashes, has no `..`, `.` or empty segment, and has no absolute or drive prefix. It isn't a symbolic link and resolves inside the pack.
- **Nothing silent.** Every `.mid` in the pack is an entry or is listed in `omitted` with a reason.
- **No fake entries.** A lane without suitable clips gets a `laneNotes` line, not a placeholder.
- **Nothing leaks.** Titles, feel and notes contain no paths or file names. The importer never puts source names in the catalog.
- **Credit is consistent.** The credit file quotes the manifest's credit line.
- **Lanes are honest.** The analyzer fails an entry when the content contradicts its lane: see the codes below.

## Analysis (`core`: `flowstate/analyze.h`, `fs-analyze`)

The analyzer reads the MIDI with core's SMF reader, then profiles, classifies, writes IR and checks it, in that order. It is deterministic: the same bytes and options always give the same analysis.

1. **Read.** SMF type 0 or 1 with a PPQ time base. Limits are 8 MB, 64 tracks and 4096 notes.
2. **Clip length.** Empty bars before the first note are trimmed. The clip ends at the bar after the last note, or at the file's end of track when that is a whole number of bars no more than twice as long. Many GodFlow files carry an end-of-track 141 bars out, which is ignored. Longer than 64 bars fails.
3. **Rolled chords.** Onsets chained less than a 64th note apart, and within a 32nd overall, count as one onset. 32nd-note runs stay separate.
4. **Profile and lane.** v1's `MidiContentProfiler` and `MidiLaneClassifier` measures and golden thresholds: primary score 60, margin 15, high confidence 80. The measures are channel-10 and GM-drum ratios, low-register ratio, single-note vs chord onsets, single-note vs several-note sounding time, and notes per onset. The bass window is C1–C4 (MIDI 24–60).
5. **Key.** Krumhansl–Kessler correlation over duration-weighted pitch classes, with the lowest note of each onset weighted 1.5×. A key is **reliable** when the best fit has r ≥ 0.70, runs at least 0.05 ahead of the next key, and the clip has at least 8 notes. Otherwise the catalog leaves the key blank and says why ("ambiguous between C major (r 0.81) and A minor (r 0.76)"). Short jazz loops are often honestly ambiguous. Detection gives major or minor only. A producer's `key` names any mode.
6. **Grid.** The coarsest grid that fits: 2, 4, 3 or 6 steps per beat, then swung 2 or 4, then 8 or 12. A grid fits when 95% of onsets are within a 64th note of a step and 60% of note ends are within a quarter step.
7. **IR, by lane.**
   - Chords: one harmony span per change of chord, named by template matching over core's own chord parser. The lowest note becomes a slash bass only when it sits a fifth or more under the voicing. The comping rhythm is a step string. The voicing family is the one whose realization matches the original pitches best, with a small cost for chords the family has to fall back on.
   - Bass: one inferred chord per bar (diatonic quality in the detected key) and chord-relative tokens (`R 3 5 7 8 a g X`). Tones the tokens can't name stay as literal notes.
   - Melody: the top line as one motif in scale degrees, with alterations and octave marks. The realizer's degree reference is reproduced exactly, so pitches round-trip.
   - Drums: one step string per IR voice (`x`, `X` accent, `g` ghost). Pitches without an IR voice stay literal.
8. **Fidelity.** The IR is realized without humanizing and compared with the original:
   - `rhythm`: onset F1.
   - `pitch`: mean pitch-class overlap of matched onsets.
   - `notes`: note F1, by exact pitch, or by pitch class for chords.
   - `literalNotes`: how many notes the IR keeps as literal notes.
   GodFlow today: rhythm 1.0 on all 29 clips; chord pitch-class overlap 0.75–1.0.
9. **Descriptors** (0..1), the same measures for every pack:
   - density: onsets per beat, saturating, so one per beat is 0.5;
   - complexity: syncopation, harmonic colour and rhythmic variety;
   - energy: velocity and density;
   - groove: straight, swing or triplet.

Failure codes, as `fs-analyze` (exit 3) and `library validate` print them:

| Code | Meaning |
| --- | --- |
| `empty`, `too_large`, `malformed`, `unsupported_timing`, `too_many_tracks`, `too_many_notes`, `no_notes` | The file can't be read as a usable SMF |
| `lane_conflict` | The manifest's lane contradicts a high-confidence classification ("the manifest says melody, but the content is clearly chords (score 92: ...)") |
| `bass_range` | A bass clip leaves C1–C4 |
| `not_drums` | A drum clip isn't all on channel 10 |
| `mixed_drums` | A pitched clip has channel-10 notes; split it per lane |
| `bad_lane`, `too_long` | Not a library lane; longer than 64 bars |

## Catalog and search

`CatalogEntry` (in `bridge.ts`) is one shape for both origins:

- A **library clip** (`lib:<pack>/<clip>`) carries `credit`: the pack, producer, credit text, license id, `allowsExport` and `allowsStyleExamples`.
- An **AI result** (`node:<id>`) is a lineage node, with its `prompt`, `kind` and `createdAtMs`.

Both carry roles, genres, key (or the reason it is blank), tempo and range, meter, bars and descriptors. Analysis-only fields (energy, density, complexity, groove) are `null` for AI results.

AI results are the session's nodes, except sketches and nodes started from a library clip. Those are listed as the clip.

Search is `core`'s `searchCatalog` (`flowstate/catalog.h`):

- **Filters:** origin, roles (any overlap), genres (any overlap), and text, where every word must appear in the title, genres, tags, feel, producer, prompt or role.
- **Without fit**, ties go to the newest AI result, then to the id.
- **With `fitContext`**, other meters are left out. Ranking adds `2 × keyFit + 2 × tempoFit` against the session's effective context. `keyFit` is the overlap of the two scales: the same key is 1, its relative 0.9, a fifth away about 0.65. An unknown key counts 0.5. `tempoFit` is 1 inside the clip's range, 0.8 at half or double time, then falls off.

### Bridge commands

Spec: `docs/bridge-spec.md`.

| Command | Effect |
| --- | --- |
| `searchCatalog { query }` | Reply carries `catalog: { total, entries }` |
| `previewEntry { entryId \| null }` | `Session.preview`. Playback in time with the host comes with the audition scheduler (P1-7) |
| `useEntry { entryId }` | A library clip becomes a `library` lineage node under the current one (undo returns to the previous idea), with `entryId` set. An AI result is selected |
| `dragEntry { entryId }` | Drags the clip as written: a library clip's normalized MIDI, or an AI result's node |

**Credit travels.** A node started from a clip keeps its `entryId`, and so do the `vary`, `edit`, `tweak` and `touch` nodes made from it. A fresh plan doesn't. Drag and export of such a node write the credit into the MIDI file as its copyright text.

## Style examples

`cloud/src/examples.ts` picks library clips for the planner to show a model. A clip qualifies when:

- its license allows style examples;
- it is in a requested lane and the request's meter;
- it shares at least one style tag with the request.

Clips that share more tags rank first, then clips whose tempo range fits; one lane is covered before a second clip in it. The request gets each clip's harmony and part as IR, with the credit, and an instruction to take the idiom, not the notes.

This is off by default (`npm run -w cloud plan -- ... --examples 2`), and `run.json` records which clips were shown. Whether it helps is for `evals` and blind listening, not opinion.

## Adding a pack

1. Put the files in `library/packs/<pack-id>/midi/<lane>/<style>/`, one clip per file, one lane per clip.
2. Write `manifest.json` (point your editor at `schema/library-pack.v2.schema.json` for checks as you type) and `CREDITS.md` quoting the credit line.
3. `npm run build:core`, then `npm run -w library validate -- packs/<pack-id>`. Every entry imports or prints its reason. Fix the entry, or move the file to `omitted` with the reason.
4. `npm run -w library build`. Review the lanes, keys and harmony it found (`library/catalog/catalog.json`). If a key is wrong and you know it, set `key`. Commit the pack and `library/catalog`.
5. Tags are a musical call. Use the planner's style vocabulary, and ask the owner where a label is a judgement.
